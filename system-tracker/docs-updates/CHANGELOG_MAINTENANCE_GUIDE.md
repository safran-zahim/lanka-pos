# Changelog Maintenance Guide

This comprehensive guide explains how to maintain your changelog system: the dual-layer approach with system-tracker daily logs and root CHANGELOG.md.

## Overview

We use a **two-layer changelog system**:

1. **Layer 1: System-Tracker Daily Logs** (`system-tracker/daily/*.md`)
   - Internal tracking of ALL changes
   - Updated after EVERY feature/fix completion
   - Comprehensive (includes pending, errors, architecture impact)
   - Enforced by pre-commit hooks

2. **Layer 2: Root CHANGELOG.md**
   - User-facing summary of notable changes
   - Generated from daily logs via semi-automatic sync
   - Cleaned up and curated (only user-visible changes)
   - Updated before releases or periodically

---

## When to Update Each Layer

### System-Tracker Daily Logs (ALWAYS)
- ✓ After completing any feature or fix
- ✓ After refactoring code
- ✓ After updating architecture or database schema
- ✓ After significant testing or quality work
- ✓ **Enforced by pre-commit hooks** — cannot commit without updating

### Root CHANGELOG.md (FROM DAILY LOGS)
- ✓ Before releasing a new version
- ✓ Weekly summary (optional)
- ✓ **Generated by sync script** — not updated manually (mostly)
- ✓ Manually curated after sync (edit, combine, clarify entries)

## Daily Log: Format & Best Practices

### Format

See `system-tracker/templates/daily-template.md` for the complete template. Here's what each field means:

```markdown
### HH:MM
- **Time**: 14:30
- **Summary**: A concise sentence describing what was done
- **Implemented**: Bullet list of changes made
- **Files touched**: List of modified files
- **File categories**: Group files by type (UI, API, Database, etc.)
- **Breaking changes**: Yes/No indicator
- **User-visible behavior**: Yes/No — KEY FOR CHANGELOG SYNC
- **Errors found**: Problems discovered during development
- **Errors fixed**: How problems were resolved
- **Pending issues**: Outstanding work or blockers
- **Testing verification**: Status of tests (unit, integration, manual)
- **Architecture impact**: None/Minor/Major
- **Next action**: What comes next
```

### Best Practices

#### 1. Keep Summaries Clear and Actionable
❌ **Bad**: "Worked on stuff"
✓ **Good**: "Fixed inventory sync not updating after batch sale"

❌ **Bad**: "Changes made"
✓ **Good**: "Implemented shadcn dialog for all POS modals"

#### 2. Be Specific with Implemented Items
❌ **Bad**: 
```
- Implemented:
  - Updated controller
  - Changed logic
```

✓ **Good**:
```
- Implemented:
  - Updated SaleController to refresh inventory cache after batch completion
  - Fixed batch quantity deduction to use Decimal for precision
  - Added verification test for inventory decrement in batch workflow
```

#### 3. Categorize Files Properly
```
- File categories:
  - UI: client/src/components/modals/DiscountModal.tsx, client/src/pages/POS.tsx
  - API: src/controllers/sales.controller.ts, src/services/inventory.service.ts
  - Database: prisma/migrations/20260301_add_batch_status.prisma
```

#### 4. Mark "User-visible behavior" Correctly

**Mark "Yes"** if users will notice/benefit:
- New features they interact with
- Bug fixes they experience
- UI/UX improvements
- Performance improvements they notice
- Breaking changes to workflow

**Mark "No"** for internal/invisible changes:
- Code refactoring (same output)
- Internal performance optimizations
- Infrastructure changes
- Dev tooling improvements
- Test coverage additions

#### 5. Document Errors & Resolutions
Always capture errors for learning:

```markdown
- Errors found:
  - Windows file system case sensitivity caused build to fail
  - Initial shadcn install broke button variant API compatibility

- Errors fixed:
  - Renamed conflicting file casing (button.tsx → Button.tsx)
  - Updated Button component to preserve existing variant props (danger, loading, fullWidth)
```

#### 6. Test Verification Status
Always indicate what was tested:

```markdown
- Testing verification:
  - Unit tests: ✓ (new test for inventory sync added and passes)
  - Integration tests: ✓ (tested full sale flow end-to-end)
  - Manual testing: ✓ (tested in POS Register — discount, tax, batch sale flows)
  - Build status: ✓ passed
```

## Writing Good Changelog Entries

### Format for CHANGELOG.md

**Good Entry**:
```markdown
- **Fixed inventory sync not updating after batch sale**
  - Updated SaleController to refresh inventory cache
  - Fixed batch quantity deduction logic
```

**What Makes It Good**:
- Clear action (Fixed, Implemented, Added, Improved)
- User-perspective (what changed for them)
- Specific (which component, what specifically changed)
- Concise (2-3 bullet points max)

### Common Entry Types

#### Feature
```markdown
- **Implemented batch processing system for bulk inventory updates**
  - Added batch creation workflow in admin dashboard
  - Added batch tracking to inventory management
  - Supports CSV import for bulk product updates
```

#### Bug Fix
```markdown
- **Fixed authentication token expiration not refreshing automatically**
  - Improved JWT refresh endpoint logic
  - Added retry mechanism for failed token refresh
```

#### UI Improvement
```markdown
- **Redesigned dashboard with modern shadcn/ui components**
  - Migrated all modals to shadcn Dialog component
  - Updated button styles for consistency
  - Improved dark mode support across all pages
```

#### Breaking Change
```markdown
- **BREAKING: Changed API response format for bulk orders endpoint**
  - Old format: `{ orders: [...] }`
  - New format: `{ data: { orders: [...] }, meta: { total, page } }`
  - Migration guide: See docs/api_documentation.md
```

## Manual Curation After Sync

### When to Edit Synced Entries

After running `npm run changelog:sync`, you may want to:

#### 1. Combine Related Entries
**Before Sync**:
```markdown
- Fixed inventory sync
- Updated inventory cache logic
- Improved inventory update reliability
```

**After Manual Curation**:
```markdown
- **Improved inventory sync reliability** 
  - Fixed cache refresh logic
  - Added automatic cache invalidation after sales
```

#### 2. Clarify Technical Language
**Auto-Generated**:
```markdown
- **Refactored QLineEdit event handler dispatch mechanism in DiscountModal**
```

**Manually Clarified**:
```markdown
- **Improved discount input handling in modal**
```

#### 3. Remove Internal Details
**Keep**:
```markdown
- **Fixed inventory sync not updating after batch sale**
```

**Remove**:
```markdown
- **Updated internal cache layer in InventoryService class method**
```

#### 4. Add Version Headers
```markdown
## [2026-03-28 to 2026-03-20]

## [2026-03-19 to 2026-03-12]

## [Previous]
```

### When NOT to Edit
- Don't change synced dates
- Don't remove entries unless duplicates
- Don't drastically reword (keep meaning clear)
- Don't move breaking changes to other sections

## Sync Workflow

### Step-by-Step Sync Process

```
1. Complete Feature/Fix
   ↓
2. Update system-tracker/daily/YYYY-MM-DD.md (enforced by pre-commit)
   ↓ (Pre-commit hook validates)
3. Commit code
   ↓
4. Merge to main branch
   ↓
5. Run `npm run changelog:sync`
   ↓ (Script reads daily logs)
6. Script extracts entries with "User-visible: Yes"
   ↓
7. Preview shown (Categorized by type)
   ↓
8. Confirm or cancel
   ↓
9. CHANGELOG.md updated
   ↓
10. Review changes: `git diff CHANGELOG.md`
    ↓
11. Commit: `git add CHANGELOG.md && git commit -m "docs: update changelog"`
```

### Sync Commands

```bash
# Preview (no changes)
npm run changelog:check

# Interactive sync (preview → confirm → apply)
npm run changelog:sync

# Check status of today's update
npm run changelog:status

# Scan past 7 days instead of 30
DAYS=7 npm run changelog:sync

# Check updates
npm run changelog:status
```

## Common Mistakes & How to Avoid

### Mistake 1: Forgetting to Mark "User-visible"

**Problem**: Ran sync but nothing appeared in CHANGELOG.md

**Solution**: 
1. Edit your daily log entry
2. Change `User-visible behavior: No` → `User-visible behavior: Yes`
3. Re-run `npm run changelog:sync`

### Mistake 2: Generic Summaries

❌ **Too Generic**:
```
- Summary: Updated code
```

✓ **Specific**:
```
- Summary: Implemented CSV import for bulk inventory updates via batch system
```

**Why it matters**: CHANGELOG readers need to understand what changed quickly.

### Mistake 3: Too Many/Too Few Details

❌ **Too Few**:
```
- Implemented:
  - Fixed stuff
```

✓ **Just Right**:
```
- Implemented:
  - Added inventory verification after batch completion
  - Fixed quantity deduction to use Decimal precision
  - Updated admin dashboard batch status indicator
```

### Mistake 4: Mixing User & Internal Changes

❌ **Mixed**:
```
- Summary: Refactored SaleController and fixed discount modal
```

✓ **Separate**:
```
- Summary: Fixed discount modal input handling
  (Document 'refactored SaleController' in separate entry if not user-visible)
```

### Mistake 5: Not Categorizing Files

❌ **Not Categorized**:
```
- Files touched:
  - src/app.ts
  - client/src/pages/Dashboard.tsx
  - prisma/schema.prisma
```

✓ **Organized**:
```
- File categories:
  - UI: client/src/pages/Dashboard.tsx
  - API: src/app.ts
  - Database: prisma/schema.prisma
```

## FAQ

### Q: What if I missed logging a change?
**A**: Add it to tomorrow's daily log (or retroactively to the date it was done). The script scans past 30 days by default, so you have time to catch up.

### Q: Can I edit CHANGELOG.md directly?
**A**: Yes, but then sync script will prepend new entries above your edits. It's better to sync regularly and let script handle most updates.

### Q: Should I create a new daily log file daily?
**A**: Pre-commit hooks enforce it. When you commit code, if today's log doesn't exist, either the commit is blocked or the hook auto-creates one (configurable).

### Q: What's the difference between breaking changes and user-visible?
**A**: 
- **User-visible**: Change that users notice (new feature, bug fix, UI update) → goes in CHANGELOG
- **Breaking**: Change that breaks compatibility → special category in CHANGELOG with migration guide

### Q: How often should I run sync?
**A**: 
- **Before releases**: Always sync before releasing a version
- **Weekly**: Optional for public updates
- **Per feature**: If you publish frequent updates

### Q: Can I skip pre-commit hook?
**A**: `git commit --no-verify` bypasses hooks, but:
1. Should only be used for emergencies
2. You must document changes within 24 hours
3. Build/CI checks might still enforce it

## Integration with Release Process

### Pre-Release Checklist

```bash
# 1. Sync changelog from daily logs
npm run changelog:sync

# 2. Review generated entries
git diff CHANGELOG.md

# 3. Manually curate if needed (combine, clarify, etc.)
# (Edit CHANGELOG.md directly)

# 4. Add version header with date
# Example: ## [v1.2.0 - 2026-03-28]

# 5. Commit
git add CHANGELOG.md
git commit -m "docs: update changelog for v1.2.0 release"

# 6. Tag release
git tag -a v1.2.0 -m "Release version 1.2.0"

# 7. Push
git push origin main --tags
```
